01 · 학습 철학

“이해했다”가 아니라 “증명했다”를 완료 조건으로

별도 실험실 repo는 만들지 않습니다. production newsletter를 실험 대상으로 삼되, 실험 코드는 최상위 lab/에 모아 src/와 섞이지 않게 합니다. check:repo-hygiene이 src/와 scripts/ 아래의 one-off 코드를 차단하므로, 실험 도구를 그 안에 두면 매주 버리고 다시 만들게 됩니다. lab/은 그 규칙 밖이라 계측 도구가 쌓이고, 쌓인 만큼 다음 주가 싸집니다.

학습 완료로 인정하지 않는 것

  • 개념 정의를 읽고 외운다.
  • 프레임워크 튜토리얼을 그대로 따라 한다.
  • Agent가 한 번 성공한 결과를 보고 “된다”고 결론낸다.

학습 완료로 인정하는 것

  • 직접 만들고 같은 조건으로 반복 실행한다.
  • 일부러 실패 조건을 주입해 어디서 깨지는지 본다.
  • 결과를 숫자로 비교하고 failure taxonomy로 원인을 분류한다.
  • 개선 뒤 동일 eval에서 좋아졌음을 증명한다.
Master rule. 이론을 설명할 수 있다 < 직접 만들 수 있다 < 일부러 망가뜨릴 수 있다 < 왜 망가졌는지 측정할 수 있다 < 다른 설계와 비교할 수 있다 < 개선 후 좋아졌음을 증명한다.

02 · 반복 방식

모든 주차는 P-B-M-F-I-E Loop로 통일

새 용어마다 다른 공부법을 만들지 않습니다. 예측부터 설명까지 같은 루프를 반복해, 개념이 아니라 문제 해결 습관을 몸에 넣습니다.

Predict먼저 결과를 예상
Build직접 구현
Measure숫자로 측정
Fail일부러 깨뜨림
Improve원인 기반 개선
Explain내 말로 일반화

예: RAG를 공부할 때

기사 100개를 전부 context에 넣는 방식, keyword retrieval top 10, retrieval + reranking top 5를 같은 query로 비교합니다. 품질·hallucination·evidence correctness·token을 측정하고 “왜 좋아졌는가?”까지 답합니다. Vector DB를 설치했다는 사실은 학습 성과가 아닙니다. 소프트웨어 세계가 늘 그렇듯 설치 성공은 문제의 시작에 더 가깝습니다.

Building & Evaluating AI Applications

Week01

측정 도구부터 만든다 — Judge Agreement

LLM judge가 사람과 얼마나 일치하는지 재고, 그 판정을 믿고 다음 실험을 쌓아도 되는지 결정합니다.

실험

동결된 candidates.json에서 calibration 20건을 뽑아 손으로 라벨하고, 같은 4개 필드(title, url, source_name, summary)만 준 judge와 비교합니다.

측정

Cohen's kappa, confusion matrix, 사람·judge 각각의 positive rate. raw agreement 대신 kappa를 쓰는 이유는 한 클래스로 collapse한 judge가 raw agreement로는 통과해 보이기 때문입니다.

핵심 질문

내가 만든 평가 기준이 실제로 재현 가능한가? 재현 안 되면 이후 모든 before/after 비교가 무의미해집니다.

왜 순서가 바뀌었나. 원래 Week 01은 reporter를 반복 실행해 비결정성을 관찰하는 것이었습니다. 그런데 runReporterStage()가 존재하지 않습니다 — reporter 호출은 gemini-newsroom-newsletter.js의 attempt loop 안에 inline이고, 그 스테이지를 덮는 행위 테스트도 없습니다. 즉 첫 주가 production 리팩터링으로 시작되고 측정값은 0개가 됩니다. 반면 src/shared/llm/llm-client.js는 이미 공개 seam이라 judge 실험은 src/를 한 줄도 안 고치고 가능합니다. 비결정성 관찰은 seam이 생긴 뒤로 미룹니다.

완료 · 2026-08-17

prompt v1prompt v2
Cohen's kappa0.5290.733
raw agreement0.800.90
불일치4건2건
judge yes 비율0.650.75 (사람과 동일)
무엇을 했나
  1. 기사 후보 20건을 사람이 손으로 “쓸 만함 / 아님” 판정
  2. 같은 20건을 LLM에게도 판정시킴
  3. 둘이 얼마나 겹치는지 셈 (그 점수가 kappa)
  4. 어긋난 건을 뜯어보고 판정 기준을 한 번 고침 → 다시 측정
무슨 일이 있었나

예측이 틀렸습니다. 시작 전에 “LLM이 나보다 대충 볼 것”이라고 적어뒀는데, 실제로는 LLM이 더 깐깐했습니다.

  • LLM은 내가 쓴 규칙을 글자 그대로 지켰습니다.
  • 규칙에 없는 논리를 끌어다 쓴 쪽은 사람이었습니다. (예: “카메라 HAL이 C++로 짜여 있으니 C++ 기사도 관련”)

그래서 어긋난 4건 중 3건은 LLM이 못 읽어서가 아니라 내 기준이 애매해서 생긴 것이었습니다. 고칠 곳도 LLM 지시문이 아니라 기준 문서였습니다.

한 줄 결론. 이 LLM은 규칙을 성실하게 따릅니다. 그래서 점수의 한계는 LLM의 실력이 아니라 내가 쓴 기준이 얼마나 정확한가입니다.

주의 — 0.733은 아직 실력이 아닙니다. 그 20건을 들여다보고 규칙을 고친 뒤 같은 20건으로 다시 잰 값이라, 오르는 게 당연합니다. 시험 문제를 보고 공부한 뒤 그 문제를 푼 것과 같습니다. 진짜 점수는 Week 02에서 한 번도 안 본 20건으로 잽니다.

상세 기록: lab/journal/week-01.md

Week02

측정 도구를 닫는다 — Held-out 검증

Week 01에서 고친 판정 기준을 손대지 않은 dev 20건에 1회 적용합니다. 이것이 judge를 계속 쓸지 정하는 진짜 게이트입니다.

남은 구멍 둘

0/N cover letter를 자립으로 볼지 정의가 침묵합니다(원인: 정의 누락). 그리고 v4l2 어휘는 있지만 카메라 프레임이 안 지나가는 항목을 judge가 통과시킵니다(원인: 읽기).

게이트

dev 20 family, 프롬프트 동결, 1회 실행, 0.60 이상 통과, 0.40~0.60 조건부, 0.40 미만 탈락. 두 단인 이유는 아래 Eval 분할 절에 있습니다.

왜 여기서 끝내나

이후 모든 주차가 “고쳤더니 좋아졌나”를 이 judge로 측정합니다. 자가 부정확하면 그 뒤 15주의 숫자가 전부 무의미해집니다.

원래 계획과 달라진 점. Week 02는 deterministic verifier 구현이었습니다. Week 01 결과가 측정 도구를 아직 못 닫았다고 말하므로 그것을 먼저 끝냅니다. verifier 구현과 reporter seam extraction은 그 뒤로 밀립니다. 계획이 데이터를 이긴 것이 아니라 데이터가 계획을 고친 것이고, 이 과정 자체가 이 커리큘럼이 가르치려는 것입니다.

완료 · 2026-08-17 · 게이트 통과

calibrationdev (held-out)
Cohen's kappa0.8860.625
raw agreement0.950.85
불일치1건3건
일반화 간격0.261
무엇을 했나

Week 01에서 고친 기준을 한 번도 안 본 20건에 딱 한 번 적용했습니다. 시험을 본 겁니다.

결과: 통과

0.625는 기준선 0.60을 넘습니다. LLM을 앞으로의 측정 도구로 채택합니다. 실행 실패 0건, 비용 $0.009.

진짜 배운 것은 통과가 아니라 “떨어진 폭”
  • 연습 문제(본 데이터): 0.886
  • 시험 문제(안 본 데이터): 0.625
  • 차이: 0.261

0.886을 실력으로 믿었다면 앞으로 15주 내내 도구를 실제보다 좋게 여겼을 겁니다. 그리고 이 차이는 데이터를 미리 떼어두지 않으면 알아낼 방법 자체가 없습니다.

왜 떨어졌나 — 한 건이 잘 보여줍니다

Week 01에서 sur40(터치스크린)을 카메라로 오인하는 문제를 고쳤습니다. 이번 시험에는 rmi4(터치패드)가 나왔습니다. 같은 종류인데 또 틀렸습니다.

즉 그 수정은 “터치 장치를 거르는 법”이 아니라 “sur40이라는 항목”을 고친 것에 가까웠습니다.

이 숫자를 너무 믿지 마세요
  • 양쪽 다 20건뿐입니다. 1건만 달라져도 점수가 0.13 움직입니다.
  • LLM 설정상 같은 걸 다시 돌려도 1건 정도는 뒤집힙니다.
  • 그래서 “차이가 있었다, 방향은 아래쪽이었다”까지만 확실합니다.

결과를 보고 기준을 고치지 않았습니다. 시험 문제를 채점한 뒤 그걸 보고 답을 고치면 그 시험은 무의미해집니다. 고칠 것 3가지는 적어만 두고, 검증은 Week 08에 쓸 마지막 31건에서 합니다.

상세 기록: lab/journal/week-02.md · 원본 실행 결과: lab/results/

Week03

Human golden

LLM judge

같은 rubric으로 자동 평가하고 human 결과와 agreement를 비교합니다.

측정

Phase 2

Context Engineering / RAG

Context를 많이 넣는 것과 필요한 정보를 잘 선택하는 것은 다른 문제라는 걸 실험으로 확인합니다.

같은 article generation task에 서로 다른 context strategy를 적용합니다.

RAG를 Vector DB 제품명과 분리해서 “필요한 정보를 찾아 context에 넣는 시스템”으로 이해합니다.

Phase 3

Using Coding Agents

Agent loop, skill, verifier, harness, observability, multi-agent를 하나씩 쌓습니다. 복잡한 framework는 가장 나중입니다.

Week07

Agent란 무엇인가

Newsletter 기능 하나를 작은 tool-calling loop로 직접 모델링합니다.

LLM → Tool → Observation → LLM → Tool → ... Tools: search_sources() read_candidate() read_evidence() validate_source() write_article() run_validator()
처음부터 LangChain 같은 framework를 필수로 두지 않습니다. 단순 loop가 무엇을 책임지는지 먼저 이해한 뒤 abstraction을 얹습니다.
Week08

Skill / Agent Context A/B Test

Skill이 “좋아 보인다”가 아니라 실제 task success를 올리는지 paired evaluation으로 봅니다.

Condition A

Agent + repo만 제공.

Condition B

Agent + repo + AGENTS.md.

Condition C

Agent + repo + AGENTS.md + 전용 Skill.

측정: Test Pass Rate, Validation Pass Rate, wrong-file modification, diff size, retry count, token, time. Skill은 문서가 아니라 intervention입니다. 효과를 재야 합니다.
Week09

Verification Loop

One-shot Agent를 없애고 bounded retry를 가진 verification loop를 만듭니다.

Agent → Implementation → test / validate ↓ FAIL Feedback ↓ Agent retry attempt_budget = 3
비교

One-shot Agent vs Verification Loop Agent.

측정

Task success, token, latency, retry, regression.

판단

재시도가 성능을 올렸는지, 단지 token만 태웠는지 구분합니다.

Week10

Harness Engineering

모델보다 모델 주변의 Controller, State, Timeout, Retry, Permission, Checkpoint, Idempotency, Sandbox, Human Gate를 설계합니다.

Chaos lab

network timeout, malformed JSON, GitHub failure, 중복 cron, process crash, validator crash.

관찰

부분 성공 상태, 중복 side effect, retry 폭주, state corruption이 발생하는지 봅니다.

핵심 질문

Agent가 이상하게 행동해도 시스템은 안전한 상태로 남는가?

Week11

Observability

“왜 틀렸지?”를 감상이 아니라 trace로 재현할 수 있게 합니다.

run_id model / prompt_version / skill_version input / context tool_calls output grader_result retry token / latency
Camera HAL에서 frame drop인데 로그가 하나도 없다면 답이 없듯, Agent도 trace가 없으면 개선이 아니라 추측을 하게 됩니다.
Week12

Multi-Agent

Agent 수를 늘리는 게 아니라 책임 분리가 실제 성능 향상을 만드는지 확인합니다.

A / B

Single Agent vs Reporter → Editor → Fact Checker.

C / D

Agent → Deterministic Verifier vs Reporter → Editor → Verifier → Repair.

측정

Quality, reliability, token, latency, failure rate.

Phase 4

Shaping the Build

구현이 싸질수록 무엇을 만들지, 무엇을 검증할지, 어떤 실패를 먼저 줄일지가 senior engineering의 중심이 됩니다.

Week13

Spec Engineering

Goal Camera HAL 엔지니어가 5분 안에 이번 주 중요한 변화를 파악한다. Constraints 근거 없는 claim 금지 source freshness 보장 generic AI article 제외 Acceptance Main article precision >= 90% Evidence binding = 100% No hard blocker
Week14

Product Sense

기술적으로 완벽한 output과 읽을 가치가 있는 제품을 구분합니다.

독자 질문

가치 질문

시간 질문

Week15

Hill-Climbing

Production trace 50–100개를 모아 가장 큰 반복 failure를 harness 개선으로 줄입니다.

Production Traces → Error Analysis → Top Failure → Harness 변경 → Regression Eval → Before / After
예: Evidence retrieval failure 31% → Context Builder 개선 → 12%. 바깥 loop는 prompt만 고치는 게 아니라 tool, grader, context, state, skill까지 개선 대상으로 봅니다.

Trigger → Harness → Context Builder → Agent ↙ ↘ Tools State ↘ ↙ Verifier ↙ ↘ PASS FAIL ↓ ↓ Human Review Feedback → Retry ↓ PR Runs → Trace → Eval → Failure Analysis → Harness Improvement → Regression Eval
졸업 기준은 “Agent를 만들었다”가 아닙니다. 실패를 관찰하고 분류하고 개선한 뒤 regression eval로 향상을 증명하는 전체 loop가 닫혀 있어야 합니다.

04 · Weekly Study Pack

매 주차 자료는 7개 artifact 역할로 생각한다

실제 repo에 학습용 폴더를 쌓는다는 뜻은 아닙니다. 각 주차를 공부할 때 아래 일곱 역할이 빠지지 않도록 개인 노트나 작업 세션에 적용하는 형식입니다.

01 concept 10–15분 개념, mental model, 흔한 오해 02 reading primary source 2–4개 03 lab 목표, 가설, 실험, 관찰, 평가, failure injection 04 starter 최소 실행 입력 / baseline 05 eval 정답지가 아니라 측정 장치 06 results 예상, 실제, 차이, failure, 수정, Before/After 07 master-check 다른 시스템에도 일반화할 수 있는지 확인

Results template

  • 내 예상은 무엇이었나?
  • 실제 결과는 무엇이 달랐나?
  • 가장 큰 failure는 무엇인가?
  • 어떤 변경 하나를 했나?
  • Before / After 수치는 어떻게 달라졌나?

Master check 예시

  • Context와 Prompt의 차이를 설명한다.
  • Context가 많을수록 나빠질 수 있는 이유를 설명한다.
  • 동일 task의 context strategy A/B test를 설계한다.
  • Token뿐 아니라 task quality까지 평가한다.
  • Newsletter가 아닌 시스템에도 같은 원리를 적용한다.

회상 게이트: 그 주 자료를 열기 전 3문항

이 커리큘럼은 앞으로만 갑니다. 그대로 두면 Week 05쯤에는 Week 01의 개념이 “본 적 있는 것”으로만 남습니다. 장기 기억은 다시 꺼내는 순간에 만들어지므로, 매 주차의 시작을 작은 회상 관문으로 엽니다.

  • 그 주 자료를 보기 전에 Week N-2의 master check에서 2문항, Week N-4에서 1문항을 골라 기억만으로 답한다.
  • 답마다 확신도(높음 / 중간 / 낮음)를 함께 적는다.
  • 답을 확인해서 틀렸거나, 낮은 확신으로 맞힌 문항은 다음 주 회상 게이트에 다시 올린다.
  • 해당 주차가 아직 없으면 있는 범위만 한다 — Week 01–02는 생략, Week 03–04는 N-2만.

통과 조건: 3문항의 답과 확신도가 그 주 journal 상단에 기록돼 있다. 전체 5분을 넘기지 않습니다.

05 · Eval 분할

개선을 증명하려면 안 본 데이터가 필요하다

졸업 조건이 “regression eval로 향상 증명”인데, 고친 데이터로 다시 재면 그건 증명이 아니라 순환 논증입니다. 그래서 데이터를 세 덩어리로 나누고 개봉 시점을 미리 못박습니다.

분할 단위는 URL이 아니라 story

같은 사건이 여러 URL로 수집기에 들어옵니다. URL 단위로 나누면 한 사건의 양쪽이 dev와 test에 갈라져 앉고, 그건 외워서 맞히는 것과 구별되지 않습니다. 저장소의 candidateGroupKey()를 그대로 씁니다 — lab과 production이 “하나의 사건”을 같은 뜻으로 쓰게 됩니다.

실측: main_eligible 후보 330건 → 71 family. 같은 시리즈의 리비전(v1·v2·v10)은 하나로 접습니다. 접는 방식은 키를 갈아끼우는 게 아니라 합집합입니다 — 메일링 리스트 id 중에는 시리즈 전체를 이미 묶고 있는 것이 있어서, 제목으로 대체하면 그 시리즈가 도리어 쪼개집니다.

배정은 한 번만 계산하고 커밋한다

수집기가 계속 돌아 후보가 쌓입니다. 정렬 후 잘라내는 방식을 매번 다시 계산하면 새 family가 들어올 때마다 기존 family가 버킷 사이를 옮겨 다닙니다. 실측하니 새 family 20개에 78개 중 10개가 재배정됐습니다.

그러면 Week 01에 손으로 라벨한 20건이 Week 02에는 다른 20건이 됩니다. 그래서 lab/datasets/split.json이 정본이고, 재실행은 재생성이 아니라 대조입니다. 새 family는 unassigned로 park합니다.

Week 01의 kappa는 통과 기준이 아니다

calibration 20건을 보고 rubric을 고친 뒤 같은 20건으로 잰 kappa는 당연히 올라갑니다. 안 오르면 그게 이상한 겁니다. 기록은 하되 합격선으로 쓰지 않습니다.

Week 01 완료 조건은 failed_cases 0, routing_warning 빈 문자열, kappa 개선 전후 둘 다 기록, 불일치 전건에 원인 분류 부착입니다. 당시 목표값은 kappa ≥ 0.40이었습니다.

진짜 gate는 Week 02

손대지 않은 dev 20 family에 Week 01에서 고친 rubric을 그대로 1회 적용합니다. 판정은 한 줄이 아니라 두 단입니다.

Week 01 kappa와 Week 02 kappa가 크게 벌어지면 rubric이 20건에 과적합된 것이고, 그 관찰 자체가 좋은 실패 사례입니다.

왜 0.60이고, 왜 두 단인가

처음에는 0.40으로 잡았습니다. 그런데 0.40~0.60은 “보통 일치” 구간입니다. 앞으로 15주 동안 모든 before/after 비교를 이 judge로 재기 때문에, 보통 수준으로 일치하는 자를 쓰면 그 노이즈가 이후 모든 숫자에 상속됩니다. 대체 평가자로 쓸 만하다고 보는 통상적 선인 0.60으로 올렸습니다.

단일 절선으로 자르지 않는 이유는 계측 해상도입니다. n=20에서 불일치 1건이 kappa를 0.133 움직입니다.

0.58과 0.62의 차이는 항목 1건도 되지 않습니다. 게다가 judge의 temperature가 0.20이라 재실행만으로 1건 안팎이 뒤집힙니다. 통계적으로 구별되지 않는 두 값을 하나의 절선으로 가르면, 그 1건이 15주의 진로를 정하게 됩니다.

두 단으로 두면 경계에 떨어졌을 때 “자를 더 다듬으면서 실험도 계속한다”는 제3의 선택지가 생깁니다. 기준을 무르게 만든 것이 아니라 계측기의 해상도에 맞춘 것입니다.

06 · Scoreboard

처음에는 7개 지표만 유지

지표를 많이 만들면 측정 체계가 좋아지는 게 아니라 대시보드가 화려해집니다. 꽤 자주 벌어지는 착시입니다. 첫 단계에서는 아래 7개만 baseline과 experiment에서 동일하게 재면 충분합니다.

모든 실험의 마지막 형식: Baseline → Experiment → Score → Comparison. 결과를 보고 “느낌상 좋아졌다”는 문장은 금지합니다.

08 · Time Allocation

공부 비율

강의 소비보다 실험과 failure analysis에 시간을 더 씁니다. “많이 읽었다”는 아주 편리한 진척 지표지만 실제 capability와의 상관은 놀랄 만큼 애매합니다.

이론 읽기 · 15%

Primary source 중심. 용어와 mental model을 잡는 데 필요한 만큼만 읽습니다.

직접 구현 · 35%

현재 newsletter 코드와 pipeline에서 작은 단위로 구현하거나 설정을 바꿔봅니다.

실험 · 25%

같은 입력으로 조건을 바꿔 A/B 비교합니다.

Failure 분석 · 15%

실패를 분류하고 가장 큰 category를 찾습니다.

내 말로 설명 · 10%

다른 시스템에 어떻게 적용할지 설명해 개념을 일반화합니다.

Graduation

16주 뒤 목표

RAG, Agent, Eval의 정의를 아는 것이 아니라 다음 흐름을 스스로 설계하고 증명할 수 있어야 합니다.

  1. 문제를 정의한다.
  2. AI가 필요한 부분을 선택한다.
  3. Context를 설계한다.
  4. Agent / Tool을 설계한다.
  5. Verifier를 만든다.
  6. Harness로 감싼다.
  7. Trace를 수집한다.
  8. Eval한다.
  9. Failure를 분류한다.
  10. 가장 큰 문제를 개선한다.
  11. 성능 향상을 regression eval로 증명한다.
