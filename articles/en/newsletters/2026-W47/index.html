01 AOSP Camera

Quirk to Bypass abortCaptures Merged to Prevent Camera HAL SIGSEGV on Galaxy A54 5G Session Stop

AndroidX Gerrit Camera (change 4430441)

A device-specific workaround (quirk) that prevents abortCaptures from being called when stopping a session only on the Galaxy A54 5G has been merged into the AndroidX main branch. This change aims to avoid abnormal termination of the driver process when quickly switching or closing the camera on this device.

Camera HAL · Driver perspective

This news is for the teams responsible for the SoC driver and HAL of the Galaxy A54 5G. This patch only prevents the upper framework from calling abortCaptures. The lower stack must separately check for null pointer references or use-after-free issues in the WNC-LmeMcscRepr routine that caused the crash.

When a camera app closes the screen or quickly switches to another camera, the framework cleans up the session. During this process, the entire process was reported to stop unexpectedly.

According to the commit message and code, the target is the Samsung Galaxy A54 5G. It uses the Exynos s5e8835 chipset, with device identifier a54x and model prefix SM-A546. On this device, calling CameraCaptureSession.abortCaptures when stopping a capture session intermittently caused a native SIGSEGV error. The error occurred in the WNC-LmeMcscRepr routine within the vendor camera library camera.s5e8835.so, resulting in the complete termination of the camera provider process.

Which devices are affected by this bypass?

A quirk is a workaround code applied only to specific devices to avoid their malfunction. The AndroidX team added Galaxy A54 5G identification conditions to the DisableAbortCapturesOnStopQuirk class. If the manufacturer is Samsung and the device name is a54x or the model name starts with SM-A546, this quirk is enabled. When the quirk is enabled, a flag is lowered in the CameraPipe graph settings to prevent abortCaptures from being called when stopping a session.

The confirmed scope from the original source includes specific variants of the Galaxy A54 5G, following some Tecno devices, Galaxy Note 10+, and Poco X3 Pro. Specific variants include SM-A546E, SM-A546U1, SC-53D, and a54xnsxx. The A53, A55, and S24 series from the same manufacturer are not included in this quirk's target.

What should you check?

Repeatedly start and stop the camera or quickly switch between front and rear cameras on the affected device. You can observe if the camera provider process crash logs (SIGSEGV in camera.s5e8835.so) disappear.

However, this patch is a workaround that avoids calls from the upper framework. It does not fix the root cause of the internal memory error in the vendor HAL library.

Is this reflected in products now?

The confirmed status is that the commit was merged into the androidx-main source tree on November 12, 2026. Whether it has been included in official CameraX distribution versions or applied through device firmware updates needs to be tracked separately.

02 AOSP Camera

Camera2-pipe CameraMetadata Adds Extension Functions to Query 3A Mode and Flash Support

AndroidX Gerrit Camera (Change 4439489)

Extension functions have been added to Camera2-pipe's CameraMetadata to query 3A mode and flash support. This allows code to easily check if the device supports a particular setting by reading static metadata arrays before creating a request.

Camera HAL · Driver perspective

This news is for sensor driver and HAL development teams during bring-up. Since the Camera2-pipe upper layer now easily queries the static 3A and flash support arrays, ensure that the supported AE, AF, and AWB mode arrays are fully populated in the static metadata.

Specifying an unsupported 3A mode when creating a camera request can lead to unexpected behavior. Therefore, it is necessary to query availability before making a request.

AndroidX patch 4439489 added isSupported extension functions to the CameraMetadata class to query 3A mode availability. These functions read the CONTROL_AE_AVAILABLE_MODES, CONTROL_AF_AVAILABLE_MODES, CONTROL_AWB_AVAILABLE_MODES, and CONTROL_AVAILABLE_MODES static keys from CameraCharacteristics. If the mode value passed as an argument is present in that integer array, it returns true; otherwise, it returns false.

How is flash mode determined?

Separate rules apply to flash modes. FlashMode.OFF is always determined to be supported, regardless of device specifications. FlashMode.SINGLE and FlashMode.TORCH return true only when the hasFlashUnit property is true. hasFlashUnit is configured based on FLASH_INFO_AVAILABLE in the static metadata. Non-standard modes return false.

This change adds helper functions for querying. It does not include logic to forcibly validate unsupported modes in the capture request pipeline or prevent request submission. It is a convenience interface that allows callers to inquire about hardware support before creating a request.

What should you check when an expected mode returns false?

The new isSupported_aeMode_returnsTrueOnlyForAvailableModes test in CameraMetadataTest expects false for AeMode.ON when the metadata key is missing or the array is empty. With ON and ON_AUTO_FLASH in the array, it expects true for both and false for OFF and ON_EXTERNAL_FLASH, which are absent from the list. The implementation uses an empty array in availableAeModes when the key is missing, so the return value alone cannot tell you whether the key is missing or the list omits the mode.

During bring-up, if an AE mode you expect to be supported returns false, start by checking CONTROL_AE_AVAILABLE_MODES from the HAL. Check whether the key is missing, the array is empty, or only the requested mode is absent. The unit test checks the query rule. Verify actual capture requests separately on a device.

This change was merged into the androidx-main source branch on November 13, 2026. Whether it has been included in official AndroidX library distributions or commercial device builds has not been confirmed.

03 AOSP Camera

CameraX SessionConfig Fast Session Switch Phase 1: Merged Dynamic UseCase Subset Switching Without Session Reconfiguration

AndroidX Gerrit Camera (Change 4381870)

Phase 1 of a fast session switch has been merged into CameraX, allowing UseCases to be changed without reopening the session. This change aims to reduce screen flickering and delays that occurred when a new session was opened every time a UseCase was changed.

Camera HAL · Driver perspective

CameraX is creating a path to change UseCase by updating only repeating requests without reconfiguring the session. This could reduce the frequency of configureStreams calls in the HAL. Instead, the stability of the pipeline in smoothly handling repeating requests where stream targets change within a single session becomes more important.

Adding or removing UseCases, such as video recording or image capture, during preview requires a complete session reconfiguration. This process causes significant time delays.

AndroidX patch 4381870 introduces a Phase 1 structure that allows changing the active subset of bound UseCases without regenerating the session. The initialEnabledUseCases method, added to SessionConfig.Builder, configures an ordered and unique list of UseCases to be initially enabled. The accompanying CameraControl.setEnabledUseCasesAsync function updates only the target output subset of repeating requests without closing the running CameraCaptureSession.

When does the switch complete and how is it verified?

This asynchronous switch call completes when the first capture result of the repeating request, reflecting the updated UseCase set, arrives. Internal framework validators proactively check compatibility with high-speed capture, extension features, concurrent cameras, zero-shutter lag, and various hardware quirks.

A safeguard is also included for cases where there is no repeating stream for a disabled subset. This mechanism automatically pre-connects a repeating stream for metering.

This change is Phase 1 and is limited to internal library use. It optimizes how sessions are operated at the framework level, rather than changing the configureStreams contract of the Camera HAL.

What should be checked?

When this feature operates, you can observe whether the upper session is not closed and only setRepeatingBurst or setRepeatingRequest is called again. This is a suggested check based on the commit content, and actual measurement results on devices have not been confirmed.

The source was merged into the androidx-main branch on November 9, 2026. Whether it has been reflected in an official AndroidX release or commercial device firmware build needs to be confirmed separately.

04 AOSP Camera

Camera2-pipe FrameGraph Buffer Frame Filtering Rework: Supporting Precise Routing Based on TagBundle

AndroidX Gerrit Camera (Change 4371710)

Camera2-pipe's FrameGraph has been changed to put frames into buffers by comparing request parameters and tags. This change fixes an issue where unintended frames entered and displaced existing buffer data when multiple buffers shared the same stream.

Camera HAL · Driver perspective

Buffers output by the HAL from the same stream are now prevented from being wasted by entering unintended buffers in the upper FrameGraph. HAL engineers should verify that all framework request metadata is returned in the results in scenarios where multiple buffer consumers share a single stream.

Consider cases where multiple buffers refer to the same camera stream. If frames requested with different settings enter an unintended buffer, the buffer can fill up prematurely, leading to frame loss.

In the previous structure, FrameGraph passed all started frames directly to all connected FrameBuffer instances. This caused side effects where one-shot captures or frames with individual settings entered other buffers, overwriting and displacing existing frames.

What is TagBundle and under what conditions does it receive frames?

AndroidX patch 4371710 changed the inspection logic to add frames to a buffer only when the frame's Request matches the parameters and tags specified for that buffer. The newly added TagBundle is an immutable set of tags. It is specified by the type of Metadata.Key and identifies frame consumers. A frame is received only if the TagBundle in Request.extras contains all the tags of the buffer.

Similar logic applies to general CaptureRequest.Key parameters. A frame is received only if the value in the request is the same as the value bound to the buffer.

The repeating requests created by FrameGraph include the union of parameters and TagBundle from all connected buffers. Therefore, repeating frames during normal operation reliably reach all buffers that meet the conditions.

How to verify and what is the reflection status?

Connect two buffers with different TagBundle instances to the same stream and request a one-shot capture with a specific tag. You can verify through unit or integration tests that frames enter only the buffer with that tag, and the queue size of other buffers remains unchanged. This is a suggested check based on the operational principles described in the commit diff.

This change was merged into the androidx-main branch on November 13, 2026. Whether it has been reflected in a final library release or product firmware build has not been confirmed.

05 AOSP Camera

PreviewView PERFORMANCE Mode Rotation Distortion Fix: SurfaceControl and TextureView Paths for CameraEffect

AndroidX Gerrit Camera (Change 4418107)

The issue where the screen appeared stretched or rotated sideways when CameraEffect or stream sharing was enabled in PreviewView's PERFORMANCE mode has been fixed. A rendering layer that corrects rotation based on the system version has been added to PreviewView.

Camera HAL · Driver perspective

This is an example of fixing a defect in the upper view when buffers output by the driver and HAL lose transformation metadata after intermediate processing by the framework. HAL developers should check that buffer flags and transformation metadata are consistently passed to the framework consumer layer.

PERFORMANCE mode uses SurfaceView for high-performance previews. In this mode, applying graphic effects or stream sharing sometimes caused screen orientation misalignment.

Why was the screen stretched or rotated sideways?

SurfaceView by default only reflects camera transformation metadata contained in the buffer onto the screen. However, for streams that have passed through CameraEffect or stream sharing pipelines, camera hardware transformation information may disappear or change in the buffer. This prevents the remaining rotation angle from being applied correctly. As a result, the preview was rotated sideways or its aspect ratio was stretched.

How is it handled differently depending on the system version?

AndroidX patch 4418107 determines if camera transformation is missing from the stream and separates the rendering method based on the API level. For API 29 and above, an intermediate SurfaceControl layer is created below SurfaceView to rotate the geometry by the remaining rotation angle. For API 31 and above, this rotation is synchronized with View transformations and is reflected immediately when the next frame is drawn.

For older devices below API 29, where SurfaceControl offers less granular control, TextureView is used for such streams. This decision is made once initially, based on the presence or absence of camera transformation in the stream. Therefore, even if a simple screen rotation occurs later, the surface is not unnecessarily destroyed and recreated.

How to verify and what is the reflection status?

With CameraEffect applied, call Preview.setTargetRotation and rotate the device screen. You can verify in a view test environment that the preview has no distortion or rotation errors without recreating the surface. This is a suggested check based on the operating principle described in the commit message.

This fix was merged into the androidx-main branch on November 10, 2026. Whether it has been reflected in library releases and actual product firmware needs to be confirmed separately.
